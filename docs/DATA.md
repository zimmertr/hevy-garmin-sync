# Data

Each upstream service, its terms, and every quirk found, dated. The spec's [section 10](SPEC.md#10-known-api-facts-verified-unless-marked) and its watch tests (F-21a, F-20a, F-27, F-30, F-31a) hold the facts verified before the build. A finding made while building or running the app goes here, dated, in the same PR as the code that relies on it. A finding first recorded in hevy-trainer-sync, the archived tool this app replaced, keeps the date it was recorded there.

## Hevy

- **Public API** (`https://api.hevyapp.com/v1`, header `api-key`): routines, routine folders, exercise templates, workout events and exercise history. Needs a Hevy Pro API key from Hevy's settings. Documented at https://api.hevyapp.com/docs. The app only reads.
- **Private API**, Hevy Trainer only (`https://api.hevyapp.com`): the API the Hevy app and web use, undocumented, signed in with the `auth2.0-token` cookie from hevy.com. Hevy can change it without notice. Hevy's terms allow suspending accounts for unauthorized use, and the README says so. The app only reads, apart from refreshing its own session.

### What the app calls

| Call | When |
|---|---|
| `GET /v1/routine_folders`, `GET /v1/routines` | Every poll. Ten per page, so a call per ten routines |
| `GET /v1/exercise_templates` | Once, on first use, a hundred per page. A template made later is read by itself |
| `GET /v1/workouts/events` | Every poll, once, with Trainer or last time's sets (`ENABLE_PREVIOUS_VALUES`) on |
| `GET /v1/exercise_history/{id}` | For last time's sets: once per exercise, the first time a synced workout holds it, and again only when the workout it came from is deleted or no longer holds it. For Trainer: only for an exercise new to its workout, once per exercise until the logged workouts are next read |
| `GET /hevy_trainer/v3/program` | Every poll, with Trainer on |
| `GET /v2/user_preferences`, `GET /hevy_trainer/user_preferences`, `GET /exercise_template_units`, `GET /user_workouts_paged` | At startup, at local midnight and after a workout event, with Trainer on |
| `POST /auth/refresh_token` | When the session has expired, about every 30 minutes |

Every call has a 30 second timeout (O-1a) and a `User-Agent` that names the app and its repo.

### Findings

- **Hevy publishes no rate limit** for the public API. Its docs ask that a job running hourly or daily not send its requests at minute :00. The app polls every minute, which that request does not speak to (read 2026-11-05, first recorded in hevy-trainer-sync).
- **Not yet seen:** a 429 from either Hevy API, or a `Retry-After` header on one. hevy-trainer-sync's records say it never got a 429 (2026-11-10). When one comes with the header, the app waits as long as it asks ([#27](https://github.com/zimmertr/hevy-garmin-sync/issues/27)).
- **Hevy has one webhook, for saved workouts.** It is set up in the "Webhooks" section of the developer settings page (https://hevy.com/settings?developer): "Subscribe to our webhook and get notified when you save a new workout." Hevy sends a POST with `{"workoutId": "<id>"}` to a URL the user gives, with an authorization header the user gives, and expects a 200 within 5 seconds. The section says nothing about routines. Hevy's published API spec has no webhook path (14 paths), so the page is the only place to set it up (2026-11-10). The app has no receiver: routines have no feed, and a receiver needs a listening port, which spec F-2 rules out.
- **Hevy's published spec** is not served as a file of its own: it sits inside https://api.hevyapp.com/docs/swagger-ui-init.js, as the `swaggerDoc` object of the script's options. The enums are schemas of their own: `CustomExerciseType` (8 exercise types), `EquipmentCategory` (9), `MuscleGroup` (20) and the `type` of `PostRoutinesRequestSet` (4 set types). `tests/data/hevy_api.json` keeps those and the 14 paths with their methods (2026-11-10, #26).
- **Routine page size** is at most 10; exercise templates take 100 (Hevy's OpenAPI spec, 2026-11-10).
- **A routine's superset field** is `superset_id`, and a set has no RPE field (OpenAPI spec, 2026-11-10).
- **Hevy's exercise list** held 451 built-in exercises on 2026-11-10. The map's ids and titles were checked against it that day: one row was missing (a second `Sled Push` id) and three had no title. Four rows are ids Hevy no longer lists; they stay, since a row nothing asks for costs nothing.
- **An exercise template's `type`** came back as `bodyweight_weighted` and `bodyweight_assisted` on 2026-11-10, where the API reference lists `bodyweight_reps` and `bodyweight_assisted_reps`. That read went through a connector, not the raw API, so the app takes both spellings.
- **A template's `equipment`** matched Hevy Trainer's own equipment value for all 447 exercises compared (2026-11-10, spec F-40).
- **A routine's weights** are kilograms with the full conversion (`22.67964547178199` for 50 lbs), and a set with a rep range carries `rep_range` with `start` and `end` (2026-11-10).
- **`GET /v1/workouts/events`** lists `updated` and `deleted` events, each with the whole workout, newest first (2026-11-05, first recorded in hevy-trainer-sync). Hevy's API reference gives a `deleted` event the workout's `id` and `deleted_at` alone, and only `updated` events are in the recorded shapes, so the app reads the id from either place (2026-11-11, #3).
- **An exercise history row and a set in a workout event name the logged numbers alike**: `weight_kg`, `reps`, `rpe`, `duration_seconds` and `distance_meters`. The row calls the set's type `set_type` and the event calls it `type`. A row names its workout with `workout_id` and `workout_start_time`, and has no index of its own (the recorded shapes, 2026-11-11, #3).
- **An exercise history lists the newest workout first, and one workout's rows in the order the sets were logged.** Checked on 2026-11-11 against a workout whose three sets differed, with TJ's okay. That read went through a connector, not the raw API. The app lists the rows as Hevy sends them (#3).
- **The session's refresh token rotates** on every refresh, and the refresh needs the old access token in `Authorization` even when it has expired (2026-11-04). The app saves the new pair before it makes another call.
- **Not yet known:** whether the session's refresh token has an absolute lifetime. The question was first recorded in hevy-trainer-sync on 2026-11-04 and is still open.
- **`/user_workouts_paged`** answered a `limit` of 10 with a 400 on 2026-11-07. The app asks for 3.
- **The program's `current_week`** is not the week the Hevy app shows ([HEVY_TRAINER_RULES.md](HEVY_TRAINER_RULES.md)).
- **The program also carries** `next_workout_index`, `program_variety`, `exercises_rotated_at` and `edits` (2026-11-04, first recorded in hevy-trainer-sync). The app reads `next_workout_index` (below) and none of the other three.
- **`exercises_rotated_at`** read Thursday 29 October 2026, so exercises do not rotate on a week boundary (2026-11-04, first recorded in hevy-trainer-sync).
- **A Trainer swap answered "Replace permanently? Yes"** in the Hevy app changes the program's `updated_at` and adds an entry to that template's `edits`: `type` `replace`, with `from_exercise_template_id` and `to_exercise_template_id`. The template's `exercises` already hold the new exercise: the edit's `from` is no longer in them, and its `to` is. So the app needs nothing from `edits`, and it rewrote the Garmin workout within one poll (2026-11-11).
- **A Trainer swap answered "No"**, for that workout only, shows in the Hevy app and nowhere else. It is in none of the replies the app reads: the program (`exercises` and `edits`), both preferences replies, the unit list and the workouts page. `user_key_values` held ten interface settings and no swap. Hevy keeps such a swap on the phone, for that one session, until the workout is saved, so nothing can read it before the session. Garmin Connect and the watch kept the old exercise (2026-11-11). Tracked in [#44](https://github.com/zimmertr/hevy-garmin-sync/issues/44). To get a swap to the watch, answer "Yes", which reaches Garmin within a minute, and swap back after the session.
- **Not yet seen live:** what the program call answers for an account with no program (the app takes a 404 or a reply without a program as "no program").
- **A row of `/exercise_template_units`** is `{id, exercise_template_id, weight_unit}`, with `id` an integer (2026-11-11). The call answered with an empty list on 2026-11-10, for an account that logs no exercise in the other unit; the app logs the shape, without values, the first time.
- **A unit set for one exercise in Hevy** (2026-11-11, one exercise set to kilograms): the app changed nothing for seven minutes, since it reads the units only at startup, at local midnight and after a workout is saved, edited or deleted (spec F-4). After a restart it gave that exercise 20 kg, the number the Hevy app showed, and rewrote one Garmin workout. [#31](https://github.com/zimmertr/hevy-garmin-sync/issues/31) holds the use case for a manual sync.
- **A Trainer template's `name`** held its key (`upper_2x_a`) on 2026-11-10, not a display name. The app reads a name in a key's form as a key, so the workout is called "Upper".
- **The first run against a real account** (2026-11-10, from a clone, Hevy Trainer on): two routines and a two-workout program became four Garmin workouts with no failure.
- **The program's `next_workout_index`** is the workout the Hevy app would start next, counted in the templates' `index` order. hevy-trainer-sync put that one workout on today from 2026-11-04 to 2026-11-10, and this app does the same since #25 (spec F-33). On 2026-11-10 it read 1, and the templates' `index` values were 0 and 1: zero-based and contiguous, so the template at that position in `index` order and the template whose `index` equals it are the same one. The program also carries `next_workout_index_updated_at`. On 2026-11-11 a reorder of the Trainer workouts in the Hevy app moved it from 1 to 0, and the app moved today's calendar entry within one poll (one scheduled, one unscheduled). Not yet seen live, as of 2026-11-11: how it moves after a logged session and across a week change. A value that is missing, not an integer or out of range is logged as a WARNING, and the app falls back to keeping the week's logged workouts off the calendar.
- **The replies' shapes were recorded** ([DEVELOPMENT.md](DEVELOPMENT.md#the-live-check)). On 2026-11-10, `make live-check`: Hevy's workout events, the five Hevy Trainer reads, and Garmin's settings, workout list, stored workout, calendar and schedule reply. On 2026-11-11, `make live-check-hevy`, after two test routines were made, one in a folder and one in none: Hevy's folders, routines, an exercise template and one row of its exercise history, and the events and Trainer reads again, unchanged (`next_workout_index` 1, template `index` values 0 and 1). Later on 2026-11-11, `make live-check` again: Garmin's stored repeat group and the steps in and around it, and a row of the unit list; then `make live-check-hevy`: `user_key_values`. `tests/data/recorded_shapes.json` keeps them, keys and types only, and every reply the fakes build is held to them (spec D-10).
- **A template carries** `secondary_muscle_groups` and `thumbnail_url` beside the fields the app reads, and **an exercise history row** carries `set_type`, `workout_start_time`, `workout_end_time`, `workout_id`, `workout_title` and `custom_metric` with the set's own fields (2026-11-11).
- **A folder's `id` is an integer**, and a routine in that folder carries the same integer as `folder_id`. The recorded routine set had `reps` null, a whole `weight_kg` sent as an integer, and neither `rep_range` nor `rpe` (2026-11-11). A routine in no folder was read but not recorded, so its `folder_id` is taken as null.
- **Routines made in Hevy reach Garmin on a poll** (2026-11-11, release 0.7.1): within a minute of the two test routines being made, the app logged `Sync: created 2, updated 0, deleted 0, scheduled 2, unscheduled 0, failed 0`.
- **Hevy's "Previous Workout Values" setting** decides which session the PREVIOUS column shows (the Hevy app's Workout Settings, read 2026-11-11, [#3](https://github.com/zimmertr/hevy-garmin-sync/issues/3)). "Any workout", the default: "Your previous exercise values will be fetched from the last time you did that exercise, regardless of routines." "Same Routine": "Your previous exercise values will be fetched from the last time you did that exercise in the current routine you are performing." The screen also says "This configuration will not be applied to Hevy Trainer workouts." Not yet known: which session a Hevy Trainer workout's PREVIOUS column shows, and whether any reply the app reads carries the setting. The recorded `user_preferences` reply has no key for it.

## Garmin Connect

Garmin's unofficial web API, through [python-garminconnect](https://github.com/cyberjunky/python-garminconnect) (MIT). Garmin's official APIs don't fit: the personal API key is read-only, and the Training API needs business access (spec section 1). Garmin may block sign-ins from cloud IPs and accounts that call too often, so the app calls Garmin only when something changed (F-4a) and leaves a second between writes (O-1b).

### What the app calls

| Call | When |
|---|---|
| The user profile | At startup and every full run: pounds or kilograms |
| The workout list, 100 per page | Every full run (startup, local midnight, after a Garmin failure) |
| Create, update or delete a workout | When a routine or Trainer workout was added, changed or removed |
| Create or update a workout Garmin refused | 5 minutes after the refusal, then at gaps that double until local midnight, then once a day; and at every full run (spec F-16) |
| Send to Device, three calls | After each create and update |
| The calendar, 31 days back through today | Every full run |
| Schedule or unschedule a workout | Every full run, when a workout is created or deleted, and when Hevy Trainer's next workout changes |

### Findings

- **python-garminconnect 0.3.20** times out API calls after 15 seconds and token calls after 30, and retries are turned off: the app has its own waits (O-1).
- **The library rewrites the token file itself** each time Garmin rotates the token. The app writes it again with a flush to disk after each call.
- **python-garminconnect 0.3.20 passes Garmin's reply on for most 429s**, so the app can read `Retry-After` (O-1, [#27](https://github.com/zimmertr/hevy-garmin-sync/issues/27)). A 429 on a read becomes `GarminConnectTooManyRequestsError`, raised from the library's `GarminConnectConnectionError` that holds the `requests` reply. A 429 on a write (create, update, delete, schedule, unschedule, and the message that sends a workout to the watch, whose two lookups are reads) is that `GarminConnectConnectionError` itself, with the reply on `.response`. A 429 on the token exchange carries no reply, so there the app waits its own 15 minutes (read in the library's source, 2026-11-10).
- **Not yet seen:** a 429 from Garmin, or a `Retry-After` header on one (2026-11-10).
- **Not yet seen:** Garmin refusing one of the app's workouts (2026-11-10). A refused workout is tried again on growing gaps (spec F-16).
- **Nothing writes outside `/data`.** On 2026-11-10 the image ran with a read-only root filesystem and no network, with made-up credentials. The app wrote its token to `/data` and waited out Hevy. Garmin's client, run on that token, failed on name resolution only. A sign-in tried all five of python-garminconnect's strategies, curl_cffi's included, and none touched a file. `login` saves no file at all: the app gives the library no token store. So neither the chart nor `compose.yaml` mounts a `/tmp` (spec O-4).
- **Weights go in the user's own unit.** A weight sent in kilograms to a pounds account showed as 0.0 lbs on a Fenix 8 (2026-11-07, spec F-21a). With Garmin Connect set to metric the app sent 20 and 22.5 kilograms. The watch, still set to pounds, showed 44.1 and 49.6 lbs, and 20 and 22.5 kg once the watch itself was set to kilograms (2026-11-10, [#5](https://github.com/zimmertr/hevy-garmin-sync/issues/5)). So the unit to send is Garmin Connect's, and the watch's weight unit is a separate setting on the watch.
- **Garmin takes every exercise category the tables use** in a strength workout: one workout holding all 42 was accepted (2026-11-10). For `BATTLE_ROPE` and `HYPEREXTENSION` the exercise Garmin stored differed from the one sent.
- **What Garmin stored for those two categories** (2026-11-10, read back, Fenix 8): for the three rows that send `HYPEREXTENSION` / `HYPEREXTENSION` and the one that sends `BATTLE_ROPE` / `BATTLE_ROPE`, the category with an empty exercise name. The other four `HYPEREXTENSION` rows (`BACK_EXTENSION_WITH_OPPOSITE_ARM_AND_LEG_REACH`, `BENT_KNEE_REVERSE_HYPEREXTENSION`, and `SUPERMAN_FROM_FLOOR` twice) were stored as sent. The watch showed the category's name for the empty ones, so no map row changes (#22).
- **`CURL` / `CURL` is stored the same way** (2026-11-11, Fenix 8): the category with an empty exercise name. `CRUNCH` / `CRUNCH` and `SQUAT` / `SQUAT` were stored as sent. A set of `HYPEREXTENSION` / `HYPEREXTENSION` and one of `CURL` / `CURL` were then recorded on the watch. The watch showed "Hyperextension" and "Curl". Garmin Connect's activity named the first set Hyperextension, with the reps the watch counted, not the 10 planned. Strava showed "Hyper Extension" and "Curl", each with its sets and weights. So an empty stored name costs nothing on the watch, in Garmin Connect or in Strava, and no map row changes.
- **A step with a `stepName` and no exercise name is accepted, and the name is dropped** (2026-11-10, Fenix 8). Garmin took a step with category `CORE`, a `stepName` and no `exerciseName`, stored `CORE` with no exercise name, and kept no `stepName`. The watch showed "Core". So a Hevy title can't reach the watch this way (#24). Not checked: what Strava shows for it.
- **Garmin stores a repeat group as a group**, not flattened (2026-11-11, Fenix 8). Read back, `HGS check set` held a plain interval step, a plain rest step, repeat groups, and interval and rest steps inside them. A group carries `type`, `stepType`, `numberOfIterations`, `smartRepeat`, `skipLastRestStep`, `childStepId`, `endCondition` and `endConditionValue` as sent, with `stepId` and `stepOrder`, and `endConditionCompare` and `preferredEndConditionUnit` null. A step inside a group carries a `childStepId` too; a plain step's is null. The workout, with a three-set repeat group and a two-round superset, was sent to the watch. `tests/data/recorded_shapes.json` keeps each kind of step under `stored_steps`.
- **Garmin took a workout of 250 steps** (2026-11-11): `HGS check steps`, with no repeat group, made and deleted at once. Larger was not tried (spec F-16).
- **A set's note on the watch** (2026-11-11, Fenix 8, `make live-check-notes`, [#3](https://github.com/zimmertr/hevy-garmin-sync/issues/3)). The first run's three notes held last time's sets as one list, such as `Prev: W 20x8, W 40x6, 65x6 @7, 65x6 @7.5, 65x5 @8`. The watch showed each whole on the note's own screen, centred and wrapped: 25 characters on 2 lines, 60 characters with a line break on 4, and 49 characters on 5. A line break in the note starts a new line on the watch. The watch wraps at a space wherever a line fills, so a list of sets can break inside one set: `W` ended a line and `40x6` began the next, and `@8` sat on a line by itself. The second run, the same day, put one set on each line. `65 lb x 6 @ RPE 7` (17 characters) stayed on one line. `45 lb x 12 @ RPE 7` (18), `65 lb x 6 @ RPE 7.5` (19) and `102.5 kg x 12 @ RPE 7.5` (23) did not: the watch moved the last word or two to a line of their own. The screen shows about six lines, and scrolls by itself through a longer note: one of 15 numbered lines showed `Line 1` to `Line 6` first. Garmin stored every note whole, that one included (110 characters). The third run, the same day, looked for a way to fit the widest likely set on one line. One line holds 14 digits: a ruler of 30 digits with no space was cut after the 14th and again after the 28th. With the unit on every line, `102.5kg x12 9.5` fit, and `102.5 kg x 12 @ 9.5`, `102.5kg x12 @9.5` and `1002.5kg x12 @9.5` did not. With the unit in a heading, `Prev (kg):`, `102.5 x 12 @ 9.5` (16 characters) and `1002.5 x12 @9.5` fit, and `1002.5 x 12 @ 9.5` (17) did not. `kg x reps @ RPE` fit on one line, and `Prev: kg x reps @ RPE` did not. A whole note of `4-6 reps`, `Prev (lb):`, `65 x 6 @ 7`, `65 x 6 @ 7.5` and `65 x 5 @ 8` showed on one screen, each on its own line.
- **The settings reply has no time zone** (its shape, recorded 2026-11-10). python-garminconnect reads the zone from the personal-information endpoint instead (spec C-7). The workout list carries each workout's `description` (2026-11-10).
- **The watch's Today prompt** (2026-11-10, Fenix 8). It listed all eight check workouts under "Dismiss", in this order: HGS check names, HGS check 1 to 5, HGS check step name, HGS check 6. Dismissed once, it came back the next time TJ started a strength activity. Garmin Connect's calendar had the app's Hevy Trainer workout on today, the one Hevy says is next. The other Trainer workout, recorded on the watch earlier that day, was not on the calendar, as spec F-33 intends. The prompt, opened that evening after the eight were added, listed the eight and not that Trainer workout. What differs between them: the Trainer entry was on today before a strength activity was recorded that day, and the eight were added afterwards. On 2026-11-11, before any activity was recorded that day, the prompt listed that Trainer workout. So the prompt offers the next Trainer workout on a day without a recorded activity. Tested on 2026-11-11: after an activity was recorded from `HGS check set` and saved, the prompt at the next strength start listed today's other workouts and not `HGS check set`, which was still in the watch's saved workouts. So the prompt drops a workout once it has been done that day and keeps the rest. The workout missing on the evening of 2026-11-10 had not been done, so that one miss stays unexplained (spec U-10).
- **The midnight full run on a real account** (2026-11-11, release 0.7.0). At 00:00 Pacific (08:00 UTC) the app started its full run, and its first Garmin call timed out: `08:00:17 ERROR Garmin can't be reached or is failing (... Read timed out. (read timeout=15)) ... Trying again in 1 min.` A minute later the run finished: `08:01:19 INFO Sync: created 0, updated 0, deleted 0, scheduled 1, unscheduled 1, failed 0`. That is one entry removed and one added, for the one Hevy Trainer workout that is next; the account had no routines. So the rollover works on a real account, and a Garmin timeout at midnight is waited out and finished by the next full run (spec O-1, F-31).
- **A workout updated in place and sent again** is one copy on the watch, with the new name and weights (2026-11-10, spec U-24).
- **A workout deleted in Garmin Connect stays in the watch's saved list** until it is removed on the watch (2026-11-10, spec F-14).
- **Garmin's exercise list** is published at https://connect.garmin.com/web-data/exercises/Exercises.json: 47 categories and 1,536 exercises on 2026-11-10. `src/hevy_garmin_sync/data/garmin_exercises.json` holds its keys (in `tests/data` until #24 moved it into the package). The first weekly comparison, on 2026-11-10, found it the same as the copy (#26).

## Strava

The app never calls Strava (spec S-1). Garmin's own Strava connection forwards the watch's recording, so the planned workout on the watch decides what Strava shows (spec G-2). These findings are why.

### Findings

- **Garmin forwards a new activity to Strava** within seconds of the phone sync, and nothing after that. A later change to the activity in Garmin Connect does not reach Strava (2026-11-05, first recorded in hevy-trainer-sync).
- **Strava shows what Garmin first forwarded.** Its API cannot edit an activity's sets or delete an activity, and has had no delete since 17 January 2017 (2026-11-05, first recorded in hevy-trainer-sync).
- **Without a planned workout the watch guesses the exercise** for each set, so the name can change from set to set within one exercise (2026-11-05, first recorded in hevy-trainer-sync).
- **The watch's FIT files store weight in sixteenths of a kilogram.** 25, 45 and 80 lb entered on the watch read 24.9, 45.1 and 80.1 lb on Strava (2026-11-05, first recorded in hevy-trainer-sync).
- **Not yet known:** whether the watch records the planned rep target or its own rep count for a set that is not edited on the watch. The question was first recorded in hevy-trainer-sync on 2026-11-05 and is still open.

## Quirks

- **kustomize 5.8 adds no namespace to a chart's resources.** Argo CD 3.5.7 runs kustomize 5.8.1, and on 2026-11-10 it refused chart 0.2.0 with "Namespace for hevy-garmin-sync apps/v1, Kind=Deployment is missing", while kustomize 5.7.1 rendered the same folder with the namespace set. The chart's templates now state `.Release.Namespace` themselves, and the `Chart` job checks it.
